# Dashboard 还能加什么

Dashboard 做好只是起点。**每家公司的帐不一样，能做的分析也不一样** ——
这个 skill 读客户帐里**实际有的资料**，据此建议，不是给一份通用清单。

## 铁律

1. **先跑分析，再开口。** 不准凭印象建议 —— 建议必须带这家公司的真实数字当证据。
2. **一次弹出一题，用 AskUserQuestion。** 不要一口气丢十个选项给老板。
3. **做不到的项目也要讲。** 讲清楚「为什么做不到」和「要怎样才能做到」，
   然后让他决定要不要为此改记帐方式。**静默略过等于替他做了决定。**
4. **不准为了让某个主题好看而编数字。** 资料不支持就是不支持。

## 第 1 步 — 跑分析

```bash
cd <dashboard 目录> && node suggest.mjs
```

（`<dashboard 目录>` 就是放 `dashboard-data.json` 的地方，通常是
`.../assets/dashboard`。找不到就先跑一次刷新。）

它会输出两组：**做得到的**（带证据）和**做不到的**（带原因）。
每一项都有 `id`、为什么、证据、怎么做。

## 第 2 步 — 逐项弹出让他选

把「做得到」那组，**依价值排序**后一题一题问。排序原则：

1. **老板会立刻拿去做决定的** 排最前（催收清单、已锁定收入、现金跑道）
2. **看得到风险的** 次之（客户集中度、银行户负余额）
3. **结构性洞察** 再次（分产品毛利、成本归属）
4. **好看但不改变决策的** 最后

每一题的选项至少要有：**加进去** / **先不要** / **解释给我听**。

⚠️ 「先不要」必须是选项。老板有权不加，但要是**知道有这个东西之后**决定不加。

## 目前 `suggest.mjs` 会检查的项目

| id | 检查什么 | 要什么资料 |
|---|---|---|
| `ar-chase` | 催收清单 / 收款效率 | 有未清应收 |
| `concentration` | 客户集中度 / 流失预警 | ≥3 个客户 |
| `seasonality` | 淡旺季 / 现金跑道 | ≥12 个月，且月营收落差 ≥2 倍 |
| `backlog` | 已收未交付（未来已锁定收入） | 有预收/押金性质的负债科目 |
| `billing-gap` | 开票 vs 营收桥接 | 两者差异 >1% |
| `product-gp` | 分产品 / 分服务线毛利 | ≥2 个营收科目且还没设 project-map |
| `attribution` | 提高成本归属比例 | 已设 project-map 但直接归属 <50% |
| `dept` | 分部门损益 | **数** deptNo 实际填写率，≥50% 才建议做 |
| `ap` | 供应商帐龄 / 付款排程 | 有采购发票**且**有未付余额 |
| `bank-negative` | ⚠ 银行户负余额 | 任何银行户余额为负 |

### 讲解时的重点

- **`backlog`（已锁定收入）通常是老板最在意的** —— 钱收了、服务还没交付。
  这个数字直接回答「我明年活不活得下去」。
- **`bank-negative` 不是加主题，是叫会计去查。** 一个银行户长期负余额，
  通常代表有笔入帐没记。
- **`attribution` 的比例就是产品毛利表可信度的上限。** 只有 9% 的话，
  线间的毛利差异有 91% 是分摊公式造出来的。
- **`dept` 永远先看填写率再讲话。** 「部门栏位是空的」和「部门栏位填了 30%」
  是两种不同的建议。

## 第 3 步 — 做他选的

选了就做，做完跑：

```bash
node render-dashboard.mjs && node headless-check.mjs
```

⚠️ **改动了取数或算法就要重新对帐**（用 `finance-dashboard-reconcile`），
而且要用一个**没拿来调参数的月份**验证。只加显示主题、没动算法就不用。

## 第 4 步 — 再问一次

做完一项，**再弹出选项问要不要继续下一项**，别自己结束。
老板通常一次只想消化一件事。

## 想加新的检查项目

`suggest.mjs` 每个检查都是一个 `add({ id, ok, title, why, evidence, how })`。
加检查的规矩：

- **`evidence` 一定要是这家公司的真实数字**，不能是描述
- **资料不支持时 `ok: false` 并写清楚原因**，不要不输出
- **不准写死结论**。（写过一次 bug：`dept` 项目直接写死「永远做不到」，
  根本没去数 —— 后来改成从 `deptCoverage` 实际计算。
  一个会说谎的建议器比没有建议器更糟。）
